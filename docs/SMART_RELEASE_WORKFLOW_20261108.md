# ArSonMix Smart Multi-OS Release Contract (2026-11-08)

## Product contract
The public website **https://masarray.github.io/arsonmix/** is the user's only
normal interaction. Download buttons start direct binary asset downloads (GitHub
Release is *storage*, never a web page the user must visit). An entirely
first-party download host/domain requires a future custom storage origin such as
an approved R2/S3 bucket with a configured domain; GitHub Pages cannot proxy
large native installers and must not pretend it does.

The landing page reads same-origin `release-catalog.json`, generated by the
Pages worker from GitHub Release metadata. Browsers do not call GitHub API
and never navigate to Releases, Actions or issues. Only exact, uploaded assets
with GitHub SHA-256 digests, an approved SHA256SUMS.txt, per-OS provenance,
immutable source commit and allowlisted original filenames appear. No dummy
Linux/macOS links or stale platform substitution. Windows may show v0.5.0-alpha.1
while other platforms say COMING SOON. Every public release refreshes catalog
once: the GitHub Actions publisher explicitly dispatches the cheap Pages
workflow (GitHub's GITHUB_TOKEN-created releases do NOT automatically fan out
to other workflows via release.published).

## Developer flow / cost budget
1. Ordinary commit: path-scoped cheap Node/Python tests only. `site/index.html`,
   `site/downloads.js` and release catalog changes must NOT schedule native
   Windows MSVC or full /preview/ Chromium. Page-only changes get a targeted
   landing browser smoke at main publish. No scheduled/nightly OS matrices.
2. Meaningful mixer/engine milestone: use existing
   `/arsonmix-ci native <exact PR HEAD SHA>` or `fat` on the PR, never both for
   the same SHA; existing CI evidence must be reused.
3. Deliberate release: create a `releases/alpha/vX.Y.Z-alpha.N` branch from
   **already reviewed main**, at most one immutable release candidate.
   Do not push this branch to trigger builders. Check that its latest HEAD,
   corresponding CMake version, and packaging notes match. Use the connected
   GitHub app to post one comment to internal issue #450:
   `/arsonmix-release vX.Y.Z-alpha.N <full 40-character candidate SHA>`.
   The owner-only dispatcher checks issue, identity, branch/SHA, earlier
   comment, already-published tags and same-SHA runs before dispatching
   the release workflow ONE TIME. No manual Actions UI.
4. Windows release job: exact checkout -> quick checks -> MSVC/61 CTest ->
   executable and /preview/ GUI hashes -> optional legal FactoryFX subset ->
   portable ZIP checks -> actual Inno install/upgrade/uninstall and private
   Show preservation -> checksum/provenance -> immutable GitHub pre-release.
   Only then request one cheap Pages catalog refresh.
5. If qualification fails: report exact failing step, do not publish, and
   repair source on a new SHA. Never spam re-runs or force-update an
   already-published tag.

## Cross-platform release readiness — no false green
Windows is currently the only **native tested and shipped** OS. JUCE source
has substantial Windows-specific startup and audio paths:
`src/Main.cpp` uses Win WebView2; `LiveAudioEngine.h` assumes
ASIO/Windows Audio/WASAPI; `src/FactoryFxRegistry.h` restricts Factory FX to
windows-x64. Porting must separate a platform-neutral mixer DSP/control graph
from platform-native device and WebView adapters. Keep the EXACT /preview/
HTML/CSS/JS and Show schema.

| Native platform | Gate before public download |
| --- | --- |
| Windows x64 | MSVC, native PCM/routing tests, verified Inno and portable |
| Linux x86_64 | JUCE CMake compile on Linux, embedded WebKitGTK WebView + ALSA/JACK/PipeWire backend, core/Show/VST3 tests, AppImage or verified portable tar, Linux provenance and SHA |
| macOS universal/arm64 | JUCE CMake compile on actual macOS with WKWebView/CoreAudio, core/Show/VST3 tests, .app / DMG, notarization/signing status honestly labeled, macOS provenance and SHA |

Porting Linux and macOS is a separate real source milestone: there are
**no authenticated Linux/macOS mixer binaries in the release now**.
Do not create only cosmetic files or call CI PASS hardware-FAT. Start with
fast source portability static tests and one native platform probe; launch
macOS paid runner only after common portability builds are viable. One
platform's failure does not block other platform's existing qualified download.
Published releases remain immutable; newer versions may be per-platform until
full tri-OS test parity is achieved. For a simultaneous tri-OS version,
publish atomically only after all three platform artifacts pass the release gate.

## Governance
Native audio device threads and callback are never modified to implement
website downloads. No private VST3 keys or unapproved binary bundling. Only
personnel authorized to publish releases can promote official assets. CI
evidence is not physical audio FAT; owners still perform controlled real-device
tests before declaring stable / production. `/preview/` remains the sole GUI.
